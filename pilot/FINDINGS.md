# 试跑结论：数据集有没有区分度（2026-11-18）

**设置**
- 数据：10 条 case，53 条 gold claim（S 36 / C 9 / U 8）。context 是 SQLite WAL 和 Redis persistence 官方文档的原文段落。
- 方法：最简 prompt，单次调用，temperature 0，JSON mode。所有 Qwen 模型都关闭了 thinking。
- 两种模式：
  - **oracle**：直接给出 gold claim，只测判定能力；
  - **e2e**：模型自己拆分再判定，和 gold 的对齐用贪心 Dice 匹配（试跑级别的对齐器）。
- 模型：qwen3.8-flash、qwen3.6-35b-a3b、qwen3.7-plus、qwen3.8-max、deepseek-v4-flash-0731、kimi-k3（均通过百炼调用）。完整的表格见 `results.md`，复现方法是依次运行 `python3 build.py && python3 run.py <models> && python3 score.py --detail`。

## 结论

1. **判定准确率已经饱和，按现在这种出题方式拉不开差距。**
   - oracle 模式下有 3 个模型 100%，2 个 98%。kimi-k3 是 87%，但掉分全部来自一条格式错误的输出，见第 4 点。
   - **6 个模型的 false-support 都是 0**：没有一条幻觉被判成 SUPPORTED。
   - 判错的只有两条：
     - qwen3.6-35b 把一条改写过的 S 判成了 U；
     - qwen3.7-plus 把我们故意设的边界 case（"main thread never waits"）判成了 C。按我们的规则应该是 U，但这条本身就有争议。
2. **区分度主要来自拆分粒度（e2e）**：e2e 准确率从 0.75（qwen3.7-plus）到 0.94（qwen3.8-max、kimi-k3）不等。小一些的模型倾向于整句不拆，S 和 C 混在一条 claim 里，最后整条判成 C（例如 pilot-05 c6/c7、pilot-06 c4/c5），里面正确的部分就丢了。
3. **引文逐字率有差异**：从 0.85 到 1.00。主要错误是用 "..." 把几段原文拼成一句，这样的引文不是原文子串。这类错误可以确定性修复（按省略号切开、分段校验），正好可以作为优化版的一个改进点。
4. **格式和鲁棒性问题**：
   - kimi-k3 有一次把结果包成了 `[{"claims": [...]}]`，外面多了一层数组，导致 schema 不对；
   - qwen3.7-plus 在"无事实内容"的 case 上编出了 2 条 claim（"The user asked a great question."）；
   - prompt 注入的 case 没有一个模型中招。
5. **延迟**（p50）：qwen3.6-35b 约 6 秒，flash 和 max 系列 10~11 秒，kimi-k3 约 19 秒。

## 对数据集设计的启示

- 现在的扰动对当前模型来说太"显眼"了。要让判定本身也有区分度，得加更难的题型：
  - 长 context 加上近似干扰：同一个数字或版本号在别的段落里指另一件事；
  - 条件和范围限定：by default / on newer versions / 充分 vs 必要；
  - 需要跨段推理才能判定的矛盾；
  - 隐含的数字推理（比如由 1000 页 ≈ 4MB 推出页大小约 4KB）；
  - 改写幅度很大、但其实正确的 S（用来测误报）；
  - **让 LLM 自然生成的回答**，这样的错误更隐蔽。
- C 和 U 的边界题（比如强度升级）会带来模型之间的分歧，但也可能带来标注噪声。规则要写清楚，题量要控制。
- 即使判定饱和，**拆分质量、引文有效率、证据完整度、格式鲁棒性、成本和延迟**这几个维度仍然能区分出 minimal 和 optimized。hill climbing 的故事可以主要围绕这几个维度来讲。
- 对齐器本身会引入误差：e2e 里的 MISSING 有一部分属于"粒度不同但内容是对的"。正式版需要 span-based 对齐，或者验证对齐器的准确率。

# 第二轮：加难版（2026-11-18）

**数据**：`spec_hard.json` 和 `cases_hard.jsonl`，共 10 条 case、130 条 gold claim（S 94 / C 17 / U 19），其中 6 条标为 contestable。
- 8 条是手工构造的：每条 context 有 9~11 个段落，题型包括近似干扰的数字和版本、被后文推翻的旧说法、"only if" 被反过来当成充分条件、一般规则的例外、文档外但现实中为真的知识、2026 年才出现的 WAL-reset bug、算术推理。
- 2 条是 glm-5.3 自然生成的回答。glm-5.3 不参加评测，生成时允许它补充文档以外的知识。

完整表格见 `results_hard.md` 和 `results_hard_noncontestable.md`。

## 结论

1. **判定准确率几乎没有被拉低。**
   - oracle 准确率在 0.96~0.99 之间；去掉 contestable 之后是 0.98~1.00。kimi-k3 是 0.84，原因跟第一轮一样，是格式问题。
   - 130 条 claim 里，5 个模型中**至少有一个判错的只有 9 条**，集中在这几类：
     - 算术：8 KB 页大小（3/5 判错），"小于 1%"（2/5）；
     - 逻辑："only if" 被反过来当充分条件（2/5）；
     - 近似干扰版本号（2/5）；
     - 版本区间蕴含（6.0 < 7.0.0）；
     - 自然回答里的范围扩大（"禁用"写成"禁用或推迟"，4/5 判错，属于 contestable）。
   - **长 context、近似干扰段落、文档外的真实知识、2026 年的新事实对这些模型都没起作用**：extrinsic_true 类型 8/8 全对。
2. **端到端的差距拉大了**：e2e 准确率从 0.68（qwen3.7-plus）到 0.87（qwen3.8-max），第一轮是 0.75~0.94。差距主要来自拆分：claim recall 在 0.75~0.89 之间，以及把对错混在一起的合并 claim。其中有一部分是贪心对齐器带来的误差。
3. **原始引文逐字率**在 0.87~1.00 之间，仍然是稳定的区分维度。
4. **kimi-k3 的格式问题会复现**：oracle 模式下 10 次里有 2 次把输出包成了 `[{...}]`。
5. **用"模型一致不同意 gold"来做标注审计是有效的**：5/5 的模型都不同意的 3 条"推导出来的建议"，对照标注规范确实应该是 U（规范允许的推理里不包括推导建议），已经改过来，并标为 contestable。这个流程值得写进 README：先看模型是否一致反对，**再按规范裁定**，而不是直接采用模型的多数意见。

## 对方案的影响

- **旗舰模型在判定上已经到顶**，minimal vs optimized 不能把判定准确率当主指标。更可行的讲法有两种：
  - 用**便宜的基座模型**（比如 qwen3.6-35b-a3b，最快，e2e 0.73，引文 0.90，提升空间大），minimal 和 optimized 用同一个模型，展示 optimized 能把它拉近到旗舰的水平，同时成本和延迟更低；
  - 主指标放在 **e2e claim 级 F1**（需要 span 对齐器）、幻觉检出率、原始→最终引文有效率、证据完整度、格式鲁棒性和成本延迟上。
- **数据集的难题要集中在推理类**：算术、only-if、版本区间、近似干扰版本号、范围扩大、丢掉条件，这些才是模型之间真正有差异的地方。长 context 和文档外知识这类题型性价比低。
- 现在真正有区分度的题只有 9 条左右，统计功效不够。正式集里推理类难题要有 40 条以上。

# 第三轮：推理题集（2026-11-18）

**数据**：`make_spec_reason.py` 生成 `spec_reason.json`，构建出 `cases_reason.jsonl`。共 11 条 case、116 条 claim：**推理类 52 条**（S 21 / C 21 / U 10），普通改写 64 条（用作误报对照），其中 4 条标为 contestable。素材新增了 PostgreSQL 的 routine vacuuming 文档。

推理题型包括：
- 算术（对的和错的都有）、跨段算术、日期差；
- 逆否命题（S）、把"only if"倒过来（U），以及倒过来后被另一段给出反例的（C）；
- 版本区间蕴含（S）；
- 语气减弱（S）、语气加强（U）；
- 忽略文档写明的例外（C）；
- 无效的传递比较（U）；
- 后来的更新推翻了旧说法（C）；
- 把充分性说过头（U）。

## 结论：推理类题终于有区分度了

oracle 模式，只看推理类且不含 contestable 的 48 条：

| 模型 | 三分类准确率 | S vs 非S | 普通改写题 | 是否 thinking |
|---|---|---|---|---|
| deepseek-v4-flash-0731 | **0.98** | 1.00 | 1.00 | 是（默认开启，每个 case 约 1 万个 reasoning token，p50 38s） |
| qwen3.8-flash | 0.92 | 0.96 | 1.00 | 否 |
| qwen3.7-plus | 0.85 | 0.92 | 1.00 | 否 |
| qwen3.8-max | 0.83 | 0.90 | 1.00 | 否 |
| qwen3.6-35b-a3b | 0.73 | 0.79 | 1.00 | 否 |
| kimi-k3 | 0.67 | 0.69 | 0.75 | 是，但 11 次里有 3 次把输出包成数组，导致整条 case 作废 |

1. **普通改写题所有模型都是 1.00，推理题的分布在 0.73~0.98**，区分度主要就来自推理题。
2. **thinking 是最大的变量**：开着 thinking 的 deepseek-v4-flash 接近满分；关掉 thinking 的 qwen3.8-max（旗舰）反而不如 qwen3.8-flash。这正好可以作为 hill climbing 里一个关键实验：同一个模型，开 thinking 和不开，或者用显式的逐步验证，对比准确率、成本和延迟。
3. **最常见的失败方式**（5 个模型里 4 个都错的）：
   - 版本区间蕴含：2.6 ≥ 2.4，结果被判成 U；
   - 跨段算术：200M / 2B = 10%，被判成 U；
   - 倒过来的"only if"被另一段推翻（同一主机 + VFS 不支持共享内存），应该是 C，被判成 U；
   - 把充分性说过头（只校验文件大小就够了），我标 U，模型判 C，这条已经改为 contestable。
4. **C 和 U 的灰色地带集中在"语气加强"上**：比如把"典型做法"说成"必须"，我们的规范判 U，2~3 个模型判 C。正式评测建议同时报告三分类准确率和 S vs 非S（也就是幻觉检出）这个二分类指标，后者对这类分歧不敏感。
5. **格式鲁棒性仍然是问题**：kimi-k3 三轮都会把输出包成 `[{...}]`。优化版的解析器应该兼容这种情况，并把它计入"修复率"。

## 对正式数据集的建议

- 以推理类题为主体，普通改写题作为误报对照，比例大约 1:1。
- 每种推理题型都配 S 和 C/U 各一，防止模型靠偏向某一边拿分。
- 标注规范要把以下几条写死：语气和量词的加强/减弱、逆否与倒置、版本区间、反例推翻。

# 第四轮：thinking 开/关对比（推理题集，2026-11-18）

`run.py` 的模型名后面加 `@think` 或 `@nothink` 就能切换 thinking。开 thinking 时走流式接口，把思考内容也收回来。对比表由 `compare_thinking.py` 生成，见 `thinking_comparison.md`。

| 模型 | thinking | 推理题（三分类） | 推理题（S vs 非S） | 普通改写题 | e2e | p50 延迟 | 平均输出 token |
|---|---|---|---|---|---|---|---|
| qwen3.6-35b-a3b | 关 → 开 | 0.73 → 0.77 | 0.79 → 0.83 | 1.00 → 1.00 | 0.83 → 0.80 | 12s → 35s | 1.6k → 5.8k |
| qwen3.8-flash | 关 → 开 | 0.92 → 0.94 | 0.96 → 0.98 | 1.00 → 1.00 | 0.86 → 0.91 | 18s → 100s | 1.6k → 8.7k |
| qwen3.7-plus | 关 → 开 | **0.85 → 0.96** | 0.92 → 0.98 | 1.00 → 1.00 | 0.82 → 0.83 | 25s → 63s | 1.4k → 4.0k |
| qwen3.8-max | 关 → 开 | **0.83 → 0.96** | 0.90 → 0.98 | 1.00 → **0.95** | 0.88 → 0.96 | 21s → **196s** | 1.1k → 11.9k |
| deepseek-v4-flash-0731 | 关 → 开（默认） | 0.96 → 0.98 | 0.96 → 1.00 | 1.00 → 1.00 | **0.60** → 0.83 | 11s → 34s | 1.1k → 3.8k |

## 结论

1. **thinking 对推理题提升明显，但不同模型收益差别很大**：qwen3.7-plus 和 qwen3.8-max 都提升了 11~13 个点；qwen3.6-35b 只提升 4 个点，它的瓶颈在模型能力本身。代价是延迟增加 2.5~9 倍，输出 token 增加 3~10 倍。
2. **thinking 也有副作用**：qwen3.8-max 开了 thinking 后想得太多，把普通改写题判成 U，准确率从 1.00 掉到 0.95，误报变多。拆分也过细，预测出 159 条 claim，而 gold 只有 116 条，precision 只有 0.72。
3. **各模型拆分粒度差别很大，这是 e2e 最大的变量**：deepseek 不开 thinking 时几乎不拆，基本按句子切，只出 80 条 claim，e2e 掉到 0.60；qwen3.8-max 开 thinking 又拆得过细。这说明**优化版需要一个独立的拆分步骤，并给出明确的原子化规则**，不能把粒度交给模型自己决定。
4. **开 thinking 之后还会错的题**集中在：
   - "语气加强"这一条（把"典型做法"说成"必须"，我们标 U，5 个 thinking 模型里 4 个判 C）；
   - 版本区间蕴含；
   - 日期算术；
   - 把文档中的比例套到具体数值上（instantiation）。

   这些更像"标注规范怎么执行"的问题，而不是能力问题。优化版的 prompt 里应该写进标注规范。

## 待决定

- **基座模型**：
  - deepseek-v4-flash（默认 thinking）判定最准、延迟适中。minimal → optimized 的提升空间主要在拆分（e2e 0.83）和引文（0.91~0.96）。
  - qwen3.7-plus 的提升故事更完整：关 thinking 0.85，开 thinking 0.96，可以把 thinking 当成一个可以归因的迭代步骤。缺点是延迟较高（63s）。
- **"语气加强"判 U 还是 C**：
  - 规则 A（严格逻辑）：文档没有明确反驳，就判 U。
  - 规则 B（语用）：文档明确给了较弱的说法（如"典型做法"），claim 说成"必须"，就判 C。
  - 模型普遍按规则 B 判。选定之后要写进标注规范，并统一 gold。

# 第五轮：换成新的模型阵容（2026-11-18）

新阵容是 deepseek-v4.1-flash、kimi-k3、glm-5.3、qwen3.8-flash、qwen3.8-max。之前用过的其他模型的结果都移到了 `archive/`。完整表格见 `lineup_report.md`，由 `lineup_report.py` 生成。

打分器现在会自动拆掉 kimi-k3 在 thinking 模式下多包的那层数组，拆过的次数单独统计在 "unwrapped" 一列。glm-5.3 有 3 次超时，原因是它默认开 thinking、思考时间超过了 180 秒；已经用 `--retry-errors --timeout 900` 补跑完毕。

## 推理题集的结果

只统计推理类 claim，不含 contestable：

| 模型 | thinking 开 | thinking 关 |
|---|---|---|
| deepseek-v4.1-flash | **1.00**（p50 27s，e2e 0.95） | 0.90（p50 7s，e2e 0.88） |
| glm-5.3 | **1.00**（p50 71s，无法关闭 thinking） | — |
| kimi-k3 | 0.98（p50 53s，e2e 0.93） | 0.90（p50 23s，e2e 0.82） |
| qwen3.8-flash | 0.94（p50 100s） | 0.92（p50 19s） |
| qwen3.8-max | 0.96（p50 196s） | 0.83（p50 21s） |

1. **开 thinking 的模型在推理题上基本都到顶了**（0.98~1.00）；关掉 thinking 后掉到 0.83~0.92。推理题集能区分的主要是"关 thinking"这种配置。
2. **deepseek-v4.1-flash 综合最好**：开 thinking 时准确率最高，e2e 也最高（第一轮 1.00 / 加难版 0.92 / 推理题 0.95），并且是开 thinking 的模型里最快的。关掉 thinking 后只要 7 秒。开和关之间正好构成一组干净的 ablation。
3. 开 thinking 的模型剩下的错误只有两条，**都落在规范的灰色地带**：
   - "语气加强"：典型做法 → 必须；
   - "充分性说过头"：只校验文件大小就够了（已标为 contestable）。
4. **关 thinking 的 qwen3.8-flash 引文逐字率只有 0.86~0.89**，开 thinking 的模型都是 1.00。

## 第一轮里几处"判错"的原因

- **qwen3.6-35b 把"checkpoint 在 1000 页时自动触发"判成了 U**。它的理由是：原文写的是"默认"在 1000 页触发，回答去掉了"默认"，就成了一个不加限定的说法。这其实是**标注规范没有覆盖到的情况**：去掉 "by default" 之后，算 S 还是 U？pilot-10 里有一条一模一样的 claim，所有模型都判了 S，说明模型自己的判断也不一致。
- **qwen3.7-plus 把"主线程从不需要等磁盘 I/O"判成了 C**（gold 是 U）。理由是原文说主线程"会尽量在没有 fsync 时写入"，言下之意是有时候需要等。这就是"语气加强"那个灰色地带，属于规则 A 还是规则 B 的问题。
- **e2e 的错误大多来自拆分**：比如把"默认策略是 no（错）……Linux 每 30 秒刷盘（对）"合成一条 claim，整条判 C，里面对的那半句也跟着丢了。还有一部分是对齐器造成的。
- **kimi-k3 的低分完全是格式问题**：thinking 模式下它会把 JSON 包成数组，整条 case 作废。把数组拆掉之后，它第一轮的成绩是 1.00。

**结论：第一轮里没有一处是明确的模型判断失误。** 两处属于标注规范的灰色地带，其余都是拆分或格式问题。

## 待定的标注规范（需要定下来，然后统一 gold）

1. 回答去掉了 "by default" / "normally" 这类限定词：算 S（语用解读），还是 U（严格逻辑）？
2. 语气加强（典型做法 → 必须，"尽量" → "从不"）：算 U（规则 A），还是 C（规则 B）？
